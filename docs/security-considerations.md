# Security Considerations

Orkestra is designed to run safely in production environments, but like any Kubernetes component, it must be deployed with care. This page outlines important security considerations, recommended practices, and areas to be aware of when operating Orkestra.

!!! note
    No security vulnerabilities have been reported for Orkestra at this time.  
    This page exists to help you adopt secure practices from the start.

---

## TLS for Webhooks

Orkestra uses Kubernetes **conversion webhooks** to support multi‑version CRDs.  
These webhooks must be served over HTTPS.

You may use:

- [cert‑manager](./user-guide/self-signed-certificate-with-cert-manager.md) (recommended)
- Your organization’s PKI
- A [self‑signed certificate](./user-guide/self-signed-certificate-with-openssl.md) (development only)

!!! warning
        Self‑signed certificates should **not** be used in production.  
        They cannot be revoked and require manual CA distribution.

Ensure that:

- The certificate includes the correct SANs  
- The CA bundle is embedded in the CRD  
- The secret containing the TLS keypair is protected  

---

## RBAC and Least Privilege

Orkestra requires permissions to:

- Watch CRDs  
- Read and write Kubernetes resources generated by templates  
- Manage finalizers  
- Serve conversion webhooks  

You should:

- Restrict Orkestra to the namespaces it manages  
- Avoid granting cluster‑admin unless necessary  
- Review the RBAC rules included in your installation manifests  

---

## Network Policies

If your cluster uses NetworkPolicies, ensure that:

- The Kubernetes API server can reach Orkestra’s webhook service  
- Orkestra can reach the API server  
- Any external registries (Git, Helm, etc.) are reachable  

---

## Secrets Management

Orkestra may interact with:

- TLS secrets  
- Registry authentication tokens  
- GitHub/GitLab tokens (via Komposer)  

Best practices:

- Use Kubernetes Secrets or external secret managers  
- Avoid embedding credentials in manifests  
- Prefer environment variables sourced from secrets  

---

## Supply Chain Security

When using registries:

- Pin katalogs to tags or commit SHAs  
- Use signed Git commits when possible  
- Validate the source of third‑party katalogs  
- Avoid executing untrusted templates  

---

## Logging and Auditing

Orkestra logs:

- Reconciliation events  
- Conversion requests  
- Errors and warnings  
- Worker activity  

You should:

- Forward logs to a centralized system  
- Enable Kubernetes audit logging  
- Monitor Orkestra’s health endpoints  

---

## Reporting Security Issues

!!! warning
    Do **not** open public GitHub issues for security vulnerabilities.

If you discover a potential security issue:

- Contact the maintainers privately  
- Provide steps to reproduce  
- Include logs or details that help assess severity  

Responsible disclosure protects the community.
