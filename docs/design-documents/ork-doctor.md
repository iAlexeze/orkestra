# ork doctor + ork deploy — Developer Experience Design

*April 2026*

---

## The problem

Developers are comfortable with Docker. They have a Dockerfile. They have a
`.env`. They know `docker run`. When it is time for production, Kubernetes is
a wall — pod specs, service accounts, ingress controllers, HPA, PDB, RBAC,
Helm charts. They either learn all of it or they hire someone who has.

Orkestra already solves this at the architecture level. A ConfigMap can be the
CRD. The operator creates every resource the app needs. The developer touches
nothing except their app code and one ConfigMap that looks like configuration,
not infrastructure.

The missing piece is the UX that makes this invisible.

---

## What the developer already has

```
my-app/
  Dockerfile        ← how to build
  .env              ← config and secrets
  .git/             ← what version to deploy
  src/              ← their code
```

That is enough. Orkestra needs nothing else to produce a production-grade
Kubernetes deployment.

---

## The flow

```
ork doctor          → examine project, show what was found
ork doctor init     → generate .orkestra/katalog.yaml
ork deploy          → build, push, apply bundle, deploy
ork open            → open the app URL from status
```

Everything happens locally. The developer never leaves VSCode.

---

## The .env contract

The `.env` file is read **locally** during `ork deploy`. It is never baked
into the image. It is never stored in the Katalog. It becomes Kubernetes
resources (Secret and ConfigMap) when the bundle is generated — applied to
the cluster once, managed by the operator thereafter.

```bash
# .env

DATABASE_URL=postgres://user:pass@host/db   # → Secret (default)
JWT_SECRET=abc123xyz                         # → Secret (default)
STRIPE_KEY=sk_live_...                       # → Secret (default)

PORT=8080                     # ork:cfg → ConfigMap (not a secret)
LOG_LEVEL=info                # ork:cfg → ConfigMap
ENVIRONMENT=production        # ork:cfg → ConfigMap
MAX_CONNECTIONS=100           # ork:cfg → ConfigMap
```

>[!Important]
>The `# ork:cfg` comment on the same line is the only convention the developer
>needs to learn. Without it: Secret. With it: ConfigMap.

The bundle command reads the `.env` at generation time, splits the variables,
and produces:

- `my-app-secrets` — a Kubernetes Secret (base64 encoded values)
- `my-app-config` — a Kubernetes ConfigMap (plaintext config values)

These are standalone generated files. They are not managed by the operator's
selector — they are applied directly, like RBAC. The Katalog references them
by name via `envFrom`.

## ork doctor

Examines the project directory and reports what Orkestra found.

```bash
ork doctor
```

```
Examining project...

  ✓ Dockerfile found
  ✓ Git repository — commit: a3f5c2b
  ✓ Language: Go  (go.mod)
  ✓ Port: 8080  (PORT in .env)
  ✓ .env — 12 variables
      4 config  (# ork:cfg)
      8 secrets (default)

Orkestra will create:
  Deployment     image built from Dockerfile, tagged :a3f5c2b
  Secret         my-app-secrets (8 variables from .env)
  ConfigMap      my-app-config  (4 variables from .env # ork:cfg)
  Service        port 8080
  Ingress        my-app.local      (frontend detected)
  HPA            min 2 / max 10
  PDB            minAvailable: 1

Run 'ork doctor init --name <my-project>' to generate .orkestra/katalog.yaml
Run with --no-secure to skip deletion protection (development mode)
Run with --no-ha to skip HPA and PDB (development mode)
```

Language detection looks for: `go.mod`, `package.json`, `pom.xml`,
`requirements.txt`, `Gemfile`, `Cargo.toml`. Port is read from `PORT` in
`.env`. If `PORT` is not found, a sensible language default is used with a
placeholder comment in the generated file.

Frontend detection: if a static build directory (`build/`, `dist/`, `public/`)
exists or if the framework is React, Vue, Angular, Next.js — Ingress is
included by default.

## ork doctor init

Generates `.orkestra/katalog.yaml` from what was found.

```bash
ork doctor init
ork doctor init --no-secure    # skip deletion protection
ork doctor init --no-ha        # skip HPA and PDB
ork doctor init --name my-app  # override project name
```

```
Generated .orkestra/katalog.yaml
Generated .orkestra/app.yaml     ← the ConfigMap the developer fills in

Next steps:
  1. Review .orkestra/katalog.yaml  (edit freely)
  2. Fill in .orkestra/app.yaml      (replicas, host, etc.)
  3. Run 'ork deploy'
```

### .orkestra/katalog.yaml (generated)

```yaml
# Generated by ork doctor init — edit freely
# Re-run 'ork doctor init' to regenerate from scratch

apiVersion: orkestra.orkspace.io/v1
kind: Katalog
metadata:
  name: my-app
  version: latest     # Modify
  description: Orkestra HA (if enabled) deployment for my-app

# Added except in --no-secure
security:
  deletionProtection:
    enabled: true

spec:
  crds:
    my-app:
      apiTypes:
        kind: ConfigMap
      labelSelector:
        ork.io/app: my-app
      allowedNamespaces: ["my-app-ns"]

      operatorBox:
        onCreate:
          namespaces:
            - name: my-app-ns

        onReconcile:
          when:
            - field: spec.image
              exists: true

          deployments:
            - name: "{{ .metadata.name }}"
              image: "{{ .spec.image }}"
              replicas: "{{ .spec.replicas | default \"2\" }}"
              envFrom:
                - secretRef:
                    name: my-app-secrets
                - configMapRef:
                    name: my-app-config
              resourceProfile: "{{ .spec.resourceProfile | default burst }}"
              reconcile: true

          services:
            - name: "{{ .metadata.name }}-svc"
              port: "{{ .spec.port | default \"8080\" }}"
              targetPort: "{{ .spec.port | default \"8080\" }}"
              reconcile: true

          ingresses:
            - name: "{{ .metadata.name }}-ingress"
              host: "{{ .spec.host | default \"\" }}"
              serviceName: "{{ .metadata.name }}-svc"
              reconcile: true
              when:
                - field: spec.host
                  exists: true

          hpas:
            - name: "{{ .metadata.name }}-hpa"
              minReplicas: "{{ .spec.minReplicas | default \"2\" }}"
              maxReplicas: "{{ .spec.maxReplicas | default \"10\" }}"
              targetCPUUtilizationPercentage: 70
              reconcile: true

          pdbs:
            - name: "{{ .metadata.name }}-pdb"
              minAvailable: 1
              reconcile: true

        status:
          fields:
            - path: phase
              value: "Pending"
              when:
                - field: spec.image
                  notExists: true

            - path: phase
              value: "Deploying"
              when:
                - field: spec.image
                  exists: true
                - field: "{{ replicasReady .children.deployment }}"
                  equals: "false"

            - path: phase
              value: "Ready"
              when:
                - field: "{{ replicasReady .children.deployment }}"
                  equals: "true"

            - path: url
              value: "https://{{ .spec.host }}"
              when:
                - field: spec.host
                  exists: true

            - path: image
              value: "{{ .spec.image }}"
```

### .orkestra/app.yaml (generated — the developer fills this)

```yaml
# This is the only Kubernetes object you manage.
# Apply it once: kubectl apply -f .orkestra/app.yaml
# ork deploy updates the image field automatically.

apiVersion: v1
kind: ConfigMap
metadata:
  name: my-app
  namespace: my-app-ns
  labels:
    ork.io/app: my-app
data:
  port: "8080"          # inferred from .env PORT
  replicas: "2"
  minReplicas: "2"
  maxReplicas: "10"
  host: ""              # fill this: myapp.example.com
  image: ""             # set by ork deploy — do not edit manually
```

The developer sees no pod spec. No service account. No resource limits until
they want them. Just the parameters of their app.

## ork deploy

Builds the image, generates the full bundle, and applies everything to the
cluster. The only command the developer runs after `ork doctor init`.

```bash
ork deploy --registry ghcr.io/myorg
ork deploy --registry ghcr.io/myorg --tag v1.2.0  # override tag (default: git commit)
ork deploy --registry ghcr.io/myorg --no-ha        # skip HPA and PDB
ork deploy --registry ghcr.io/myorg --dry-run      # show what would be applied
```

### What ork deploy does, in order

```
1. Build
   docker build -t ghcr.io/myorg/my-app:a3f5c2b .

2. Push
   docker push ghcr.io/myorg/my-app:a3f5c2b

3. Generate bundle
   ork generate bundle -k .orkestra/katalog.yaml -o .orkestra/bundle/
   This generates:
     .orkestra/bundle/rbac.yaml        (ServiceAccount, Role, RoleBinding)
     .orkestra/bundle/configmap.yaml   (the Katalog ConfigMap for Orkestra)
     .orkestra/bundle/namespaces.yaml  (my-app-ns)

4. Generate secrets from .env (new step — not part of existing bundle)
   Read .env → split by # ork:cfg tag →
     .orkestra/bundle/app-secrets.yaml    (Kubernetes Secret, base64)
     .orkestra/bundle/app-config.yaml     (Kubernetes ConfigMap, plaintext)

5. Apply bundle
   kubectl apply -f .orkestra/bundle/

6. Install Orkestra if not present
   helm install orkestra ...

7. Patch CR image field
   kubectl patch configmap my-app -n my-app-ns \
     --patch '{"data":{"image":"ghcr.io/myorg/my-app:a3f5c2b"}}'

8. Watch until ready
   kubectl get configmap my-app -n my-app-ns -o jsonpath='{.data.phase}' -w
```

## The secret generation — key implementation detail

This is the step that makes the .env model safe. The `.env` file is read
locally. The generated Secret file is applied to the cluster once. After that,
the developer manages secrets by:

- Editing `.env` and re-running `ork deploy` (regenerates and re-applies the Secret)
- Or editing the Kubernetes Secret directly for production changes

The generated Secret is a standard Kubernetes Secret:

```yaml
# .orkestra/bundle/app-secrets.yaml
# Generated by ork deploy — DO NOT COMMIT THIS FILE
# Add .orkestra/bundle/ to .gitignore

apiVersion: v1
kind: Secret
metadata:
  name: my-app-secrets
  namespace: my-app-ns
type: Opaque
data:
  DATABASE_URL: cG9zdGdyZXM6Ly8...   # base64
  JWT_SECRET: YWJjMTIzeHl6...         # base64
  STRIPE_KEY: c2tfbGl2ZV8...         # base64
```

**`.orkestra/bundle/` goes in `.gitignore`.** The generated secrets never
enter source control. `ork deploy` regenerates them from the local `.env`
on every run.

The `.gitignore` entry is added automatically by `ork doctor init`:

```
# Added by ork doctor init
.orkestra/bundle/
```

The `.orkestra/katalog.yaml` and `.orkestra/app.yaml` are committed — they
contain no secrets, only structure and configuration values.

## --no-ha

```bash
ork doctor init --no-ha   # generates katalog without HPA and PDB
ork deploy --no-ha        # deploy flag (overrides what's in katalog)
```

Without `--no-ha` (default):
- HPA: min 2 replicas, max 10, target CPU 70%
- PDB: minAvailable 1
- Deployment: 2 replicas

With `--no-ha`:
- Single replica
- No HPA, no PDB
- Right for: development clusters, kind, staging, personal projects

## The VSCode extension

Four things only:

**1. CLI installation**
On first open, checks for `ork` in PATH. If missing, prompts to install.
One click. Uses the install script.

**2. Intellisense on `.orkestra/katalog.yaml`**
Autocomplete, hover documentation, inline validation errors.
Driven by the Katalog JSON schema — the same schema that powers `ork validate`.
Template expressions get basic syntax highlighting.

**3. Status bar**
Shows current deployment phase while you work:
`my-app: Ready ✓` or `my-app: Deploying...` or `my-app: Not deployed`
Reads from `ork status` on a 10-second poll. Clicking opens the Control Center.

**4. Command palette**
- `Orkestra: Initialize Project` → `ork doctor init`
- `Orkestra: Deploy` → `ork deploy`
- `Orkestra: Open App` → `ork open`
- `Orkestra: Open Control Center` → `ork control start`

No terminal required for the happy path.

## What the developer does

From zero to production Kubernetes in five steps, none of which require
knowing what a pod is:

```
1. Install the VSCode extension
   → ork CLI installed automatically

2. Open your project
   → Command palette → "Orkestra: Initialize Project"
   → .orkestra/katalog.yaml generated
   → .orkestra/app.yaml generated

3. Fill in .orkestra/app.yaml
   → host: myapp.example.com
   → maxReplicas: 20   (optional)

4. Deploy
   → Command palette → "Orkestra: Deploy"
   → enter registry: ghcr.io/myorg
   → done

5. ork open
   → browser opens myapp.example.com
```

They wrote no YAML that wasn't about their app.
They learned no Kubernetes concepts.
They have HPA, PDB, Ingress, secrets management, and a live status view.

## v1 scope

Ships with `ork doctor` and `ork deploy`:
- `.env` parsing with `# ork:cfg` tag
- Language and port detection
- Katalog and CR generation
- Bundle generation including app secrets and config
- Docker build and push
- Orkestra auto-install if not present
- CR image patch and readiness watch
- `--no-ha` flag
- `.gitignore` update for generated bundle

VSCode extension: v1.1 — the CLI is the foundation, the extension wraps it.

Vault provider: v2 — the pattern (ork:cfg / ork:secret / ork:vault tags) is
designed now so the convention is stable when Vault lands.
