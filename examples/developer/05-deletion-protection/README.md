# Example 05 — Deletion Protection

Your deployed app is protected from accidental deletion by default.
This example shows what that means in practice and how to clean up properly when you're done.

**What you learn:**

- Why `kubectl delete` is blocked for Orkestra-managed resources
- How to disable protection before decommissioning an app
- The right cleanup sequence

!!! note
    Deletion protection is **on by default** in every katalog generated by
    `ork doctor init`. You don't need to configure anything for this example —
    you've already been running with it since example 01.

---

## What protection means

When Orkestra starts with `security.deletionProtection.enabled: true` in the Katalog,
it registers a webhook that intercepts every `DELETE` request for your app's resources.
Any attempt to delete a protected resource is rejected before it reaches the cluster.

This protects:
- Your app's ConfigMap CR (`my-api-orkestra`)
- The Deployment, Service, HPA, PDB Orkestra created
- The Orkestra operator itself (runtime, control center, RBAC)

---

## Step 1 — Try deleting a running app

With `my-api` deployed, try deleting it:

```bash
kubectl delete configmap my-api-orkestra -n my-api-orkestra-ns
```

Expected:

```
Error from server: admission webhook "protect.resources.orkestra.orkspace.io" denied the request:

[Orkestra Security] "my-api-orkestra" is protected from deletion.

To delete it:
- Set security.deletionProtection.enabled: false in the Katalog
- Redeploy Orkestra, then delete the resource.
```

Try the namespace:

```bash
kubectl delete ns my-api-orkestra-ns
```

Same result — the namespace is protected too.

---

## Step 2 — Observe protection in the Control Center

1. Open [http://localhost:8081](http://localhost:8081)
2. Click `my-api` — the Katalog card shows a **Protected** badge
3. Click **View Resources** → click the CR
4. Scroll to the **Security** section — deletion protection status is `enabled`

Every blocked deletion attempt is recorded here with a timestamp and the user
identity that attempted it.

---

## Step 3 — Decommission correctly

To remove the app, disable protection first. Open `.orkestra/katalog.yaml`:

```yaml
security:
  deletionProtection:
    enabled: false    # change this
```

Redeploy so Orkestra picks up the change:

```bash
ork deploy --registry ghcr.io/myorg
```

Watch the Orkestra logs confirm the webhook is removed:

```json
{"level":"info","message":"deletion protection webhook removed"}
{"level":"info","message":"tls secret removed on shutdown"}
```

Now deletion succeeds:

```bash
kubectl delete configmap my-api-orkestra -n my-api-orkestra-ns
# configmap "my-api-orkestra" deleted
```

Orkestra detects the CR is gone and removes all child resources (Deployment,
Service, HPA, PDB) automatically via owner references.

---

## Step 4 — View the decommission in the Control Center

1. Refresh [http://localhost:8081](http://localhost:8081)
2. The `my-api` Katalog card still appears — the Katalog definition lives in Orkestra,
   not in the CR
3. Click **View Resources** — the list is now empty (CR was deleted)
4. The **Events** tab on the previous CR (if you cached the URL) shows the deletion event

---

## Using --no-secure for development

When iterating quickly you probably don't want to go through the disable/redeploy
cycle just to clean up a test deploy. Use `--no-secure`:

```bash
ork doctor init --name my-api --no-secure
ork deploy --registry ghcr.io/myorg --no-secure
```

`--no-secure` skips deletion protection labels and the webhook entirely.
Resources can be deleted freely. Recommended for local `--dev` workflows.

!!! caution
    Never use `--no-secure` for production deployments. Deletion protection
    exists to prevent `kubectl delete` accidents from human operators with broad
    cluster permissions.
