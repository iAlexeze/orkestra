# Example 04 — Notifications

Get an email or Slack message the moment your deployment stalls — with the exact
`kubectl` command to check logs and a one-liner to roll back.

No Prometheus. No PagerDuty. No custom alerting rules.
It's wired into every katalog by default — you just need to tell Orkestra who to notify.

**What you learn:**

- How `--notify-me` wires your Git email and `.env` SMTP/Slack credentials into a team
- The `orkestra-notification` Secret and why credentials never touch the Katalog YAML
- What the `developer` team notification looks like on email and Slack
- How to trigger a notification on purpose to test it

!!! note
    Complete [Example 01](../01-one-project/README.md) first.

---

## How it works (60-second overview)

Every katalog generated by `ork doctor init` already contains this:

```yaml
when:
  - field: "{{ replicasReady .children.deployment }}"
    equals: "false"
    notify:
      teams: [developer]
      message: "{{ .metadata.name }} is deploying but replicas are not ready yet.
        Check logs: kubectl logs -n {{ .metadata.namespace }} -l ork.io/app={{ .metadata.name }} --tail=50
        | Roll back if stuck: ork doctor deploy rollback"
```

The `developer` team reference is a no-op until you configure it.
`--notify-me` does the configuration — automatically, from sources you already have.

---

## Step 1 — Add credentials to .env

Open `my-api/.env` and uncomment the SMTP and/or Slack lines:

```bash
# Email — all five vars required for email delivery
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=you@example.com
SMTP_PASS=your-app-password
SMTP_FROM=you@example.com

# Slack — just the webhook URL
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/T.../B.../...
```

!!! note "Gmail"
    Use an [App Password](https://myaccount.google.com/apppasswords) — not your
    account password. Enable 2-factor authentication first.

!!! note "Slack webhook"
    Create an Incoming Webhook at https://api.slack.com/apps.
    The URL is workspace-specific. One webhook URL → one channel.

---

## Step 2 — Check what ork doctor sees

```bash
cd my-api
ork doctor
```

Because SMTP or Slack vars are now in `.env`, `ork doctor` prints a hint:

```
  ~ SMTP/Slack detected in .env
    Run 'ork doctor init --name my-api --notify-me' to wire notifications.
    Orkestra will create an orkestra-notification Secret and notify your team
    on deployment status changes.
```

---

## Step 3 — Re-init with --notify-me

```bash
ork doctor init --name my-api --notify-me
```

Open `.orkestra/katalog.yaml` and find the new notification block:

```yaml
notification:
  enabled: true
  defaults:
    interval: 15m
    # slackWebhookUrl injected via SLACK_WEBHOOK_URL in orkestra-notification Secret
  teams:
    developer:
      email:
        - you@example.com     # from git log -1 --pretty=format:%ae
      slack:
        - "#deployments"      # present when SLACK_WEBHOOK_URL is in .env
      message: "{{ .metadata.name }}: {{ .status.phase }}"
```

Your credentials never appear in the Katalog. Orkestra reads them from a Secret.

Open `.orkestra/values.yaml` and find the new section at the bottom:

```yaml
runtime:
  extraEnvFrom:
    - secretRef:
        name: orkestra-notification
```

This mounts the Secret into the Orkestra runtime as env vars.

---

## Step 4 — Deploy

```bash
ork doctor deploy --registry ghcr.io/myorg
```

After applying the bundle, watch for:

```
  ✓ orkestra-notification Secret applied
```

This Secret lives in `orkestra-system` and contains your SMTP and Slack credentials
mapped to the env var names `pkg/konfig` expects:

```yaml
stringData:
  SMTP_HOST: "smtp.gmail.com"
  SMTP_USER: "you@example.com"
  SMTP_PASS: "..."
  SLACK_WEBHOOK_URL: "https://hooks.slack.com/..."
```

Orkestra reads these values when sending notifications. They never appear in your
Katalog YAML, your ConfigMap, or your app's own Secret.

## Step 5 — Trigger a notification

Deploy a broken image (same as in example 03):

```bash
# In main.go, add at the top of main():
//   panic("testing notification")
git add . && git commit -m "trigger notification test"
ork doctor deploy --registry ghcr.io/myorg
```

Within 15 minutes of the replicas failing to become ready, you will receive:

**Email:**

```
From: you@example.com
Subject: [orkestra] replicasReady condition triggered

my-api is deploying but replicas are not ready yet.
Check logs: kubectl logs -n my-api-orkestra-ns -l ork.io/app=my-api --tail=50
Roll back if stuck: ork doctor deploy rollback
```

**Slack:**

```
my-api is deploying but replicas are not ready yet.
Check logs: kubectl logs -n my-api-orkestra-ns -l ork.io/app=my-api --tail=50
Roll back if stuck: ork doctor deploy rollback

[Katalog: my-api]  [Team: developer]
```

The notification fires once and then respects the 15-minute interval — no spam
while the condition stays true. On Orkestra restart, the clock resets.

---

## Step 6 — Roll back and verify silence

```bash
ork doctor deploy rollback
```

Once replicas become ready, `replicasReady` evaluates to `true` — the condition is
no longer true and no further notifications are sent.

---

## Step 7 — View the notification Secret in the Control Center

1. Open [http://localhost:8081](http://localhost:8081)
2. You should see `my-api` in `Ready` state
3. The notification was delivered — no new pages appear in the Control Center
   for this, but the **Events** tab on the CR shows the reconcile timeline
   including the phase transitions that triggered the condition

!!! tip
    Notifications are logged at the Orkestra runtime level. If a notification
    fails to deliver (bad SMTP password, expired webhook), the reconcile
    continues — delivery failure is never fatal.
