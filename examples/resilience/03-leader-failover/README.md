# Leader Failover — Leader Election Resilience

Orkestra uses Kubernetes leader election to ensure that only one replica — the **konductor** — runs reconcilers at a time. Followers stand by, ready to take over if the leader disappears. When the konductor pod is killed, a new leader is elected within the configured `leaseDuration` and reconciliation continues without interruption.

This example uses a helm-deployed runtime with `replicaCount: 2` to show that the runtime is highly available. The local `ork run` command is single-replica and cannot demonstrate failover.

**What you learn:** How to configure leader election in the Orkestra helm chart, how to inspect the `orkestra-konductor` Lease, what happens when the leader pod is killed, and how to verify the new leader is serving authoritative state.

## Step 6 — Install Orkestra via helm

```bash
helm repo add orkestra https://orkspace.github.io/orkestra
helm upgrade --install orkestra orkestra/orkestra \
  -f values.yaml \
  --namespace orkestra-system --create-namespace \
  --wait --timeout 120s
```

The `values.yaml` configures:

```yaml
runtime:
  replicaCount: 2

  leaderElection:
    enabled: true
    leaseDuration: 15   # seconds — follower wait before declaring leader lost
    renewDeadline: 10   # seconds — leader retry window before yielding
    retryPeriod: 5      # seconds — follower retry interval
```

Wait for the runtime deployment to be ready:

```bash
kubectl rollout status deployment/orkestra-runtime -n orkestra-system
```

## Step 7 — Inspect the leader election lease

```bash
kubectl get lease orkestra-konductor -n orkestra-system
```

```text
NAME                  HOLDER                                 AGE
orkestra-konductor    orkestra-runtime-<holder-pod>          30s
```

```bash
kubectl describe lease orkestra-konductor -n orkestra-system
```

```text
Spec:
  Holder Identity:         orkestra-runtime-<holder-pod>
  Lease Duration Seconds:  15
  Lease Transitions:       0
  Renew Time:              2026-07-02T09:49:27Z
Events:
  Normal  LeaderElection  30s  orkestra runtime  orkestra-runtime-<holder-pod> became leader
```

`Lease Transitions: 0` — no failover yet. `Holder Identity` is the pod that won the election. `Lease Duration Seconds: 15` matches what was set in `values.yaml`. `Renew Time` is updated by the leader on every renewal cycle — if it stops updating, a follower will declare the lease expired and take over.

---

## Step 8 — Check the leader's logs

```bash
kubectl logs orkestra-runtime-<holder-pod> -n orkestra-system | grep konductor
```

```text
{"level":"info","message":"orkestra-runtime-<holder-pod> 🏆 became konductor, starting kordinator..."}
```

Only the konductor pod emits this line. Follower pods are silent — they are waiting.

---

## Step 9 — Apply the CR

```bash
kubectl apply -f cr.yaml
```

The leader reconciles. Its logs show:

```text
{"level":"info","message":"reconciled resilience.demo.orkestra.io/v1alpha1, Kind=BlockchainApp"}
```

This confirms which pod is performing the work.

---

## Step 10 — Kill the konductor pod

```bash
kubectl delete pod <holder-pod> -n orkestra-system
```

The pod is deleted. Kubernetes starts a replacement immediately, but it begins as a follower — it must first win the election.

Watch the pods and lease simultaneously:

```bash
kubectl get pods -n orkestra-system -w &
kubectl get lease orkestra-konductor -n orkestra-system -w
```

Within `leaseDuration` (15s), a follower acquires the lease.

---

## Step 11 — Inspect the lease again

```bash
kubectl describe lease orkestra-konductor -n orkestra-system
```

```text
Spec:
  Holder Identity:         orkestra-runtime-<holder-pod>-2    ← new pod
  Lease Duration Seconds:  15
  Lease Transitions:       1                            ← incremented
Events:
  Normal  LeaderElection  4m   orkestra runtime  orkestra-runtime-<holder-pod> became leader
  Normal  LeaderElection  12s  orkestra runtime  orkestra-runtime-<holder-pod>-2 became leader
```

`Lease Transitions: 1`. The second event confirms the new leader. Check its logs:

```bash
kubectl logs <new-holder-pod> -n orkestra-system | grep konductor
```

```text
{"level":"info","message":"orkestra-runtime-<holder-pod>-2 🏆 became konductor, starting controller..."}
```

The StatefulSet and Service are still running — no resources were lost during failover.

## E2E

```bash
ork e2e
```

Exercises the full arc — leader elected, CR reconciled, leader pod killed, new election within `leaseDuration`, new leader serving authoritative state, resources intact after failover.

This example uses `custom.target: kubernetes` — the universal test harness that manages a kind cluster and runs any Kubernetes workload without assuming an Orkestra-managed install. Orkestra itself is installed via `setup.helm`, just like any other chart. For more: https://orkestra.sh/docs/guides/e2e-universal/

Uses `leaderElection` on both `kubectl.port-forward` and `kubectl.logs` so assertions always target the current holder — the new pod after failover.

For more on testing leader-led deployments: https://orkestra.sh/docs/concepts/e2e/leader-led-deployments/
